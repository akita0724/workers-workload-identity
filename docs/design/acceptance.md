# Acceptance criteria and validation plan

**Status:** Target design. This document is a test plan for the design; it does not mean that the project currently passes every gate. Requirement IDs refer to the [requirements](./requirements.md).

## 1. Architecture validation

| ID   | Pass condition                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A-01 | Public HTTPS exposes discovery and JWKS on the OIDC routes and forwards `/admin/` to the Admin Worker. The issuance RPC cannot be called directly over HTTP and is callable only through a Service Binding.                                                                                                                                                                                                                                                                                                                                                                |
| A-02 | Issuance fails when `ctx.props.clientId` is missing, invalid, unknown, or disabled. An RPC argument or HTTP header cannot override caller identity.                                                                                                                                                                                                                                                                                                                                                                                                                        |
| A-03 | The selected libraries sign, verify, and export JWKs with RS256 in the Worker runtime. Enabling ES256 requires the same test with a P-256 key. Tests detect dependencies on Node-only APIs.                                                                                                                                                                                                                                                                                                                                                                                |
| A-04 | In a production-like account, inventory the effective permissions of administrators, Worker editors, and CI/API tokens. A principal outside the account cannot deploy a Service Binding to the issuer. A distrusted in-account principal cannot successfully issue by setting another caller's `props.clientId`; verify this with a negative live test. If all deployment principals share one trust boundary, document its scope and change auditing. Central CI is not a pass condition. Issuance through a public handler and loopback binding must also be impossible. |
| A-05 | The issuer's public host forwards `/admin/` to a separate Admin Worker, and unauthenticated clients cannot reach administrative data. The Admin Worker has neither signing private keys nor an issuance RPC binding.                                                                                                                                                                                                                                                                                                                                                       |
| A-06 | Disabling a client or removing a grant in Policy D1 causes the issuer's next request to fail. Read failures fail closed. The issuer has no Admin D1 binding.                                                                                                                                                                                                                                                                                                                                                                                                               |
| A-07 | The Admin Worker has no Key Registry D1 binding, private key, or Cloudflare Worker update token. The Controller rejects operations outside its allowlist, arbitrary target Workers, and supplied key material.                                                                                                                                                                                                                                                                                                                                                             |
| A-08 | Public keys in Key Registry D1 match the JWKS. Policy D1 changes by the Admin Worker cannot change a public JWK or the `active` key.                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| A-09 | Admin SPA deep links and `/api/*` routes are separated correctly, and the API never returns an HTML fallback. The public passkey shell and assets contain no admin data. In Access mode, the entire admin path on the public host is protected.                                                                                                                                                                                                                                                                                                                            |

## 2. Issuance and verification

| ID   | Pass condition                                                                                                                                                                                                                                                                                                                    |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-01 | An authorized caller obtains a JWT for an allowed `aud`; `iss`/`sub`/`aud`/`iat`/`nbf`/`exp`/`jti`, the audience-selected `alg`, and `kid` have the expected values.                                                                                                                                                              |
| T-02 | Issuance rejects an unknown or disabled client, missing or invalid `ctx.props`, and invalid `aud`. The relying party rejects a bad signature, unknown `kid`, expiry, and a future `iat`.                                                                                                                                          |
| T-03 | A caller cannot choose `sub`, lifetime, signing algorithm, or additional claims through its input. A mismatch among `kid`, key type, and `alg` is rejected.                                                                                                                                                                       |
| T-04 | A relying party rejects a JWT used with another `aud`, another `iss`, another token purpose, or an unapproved `sub`.                                                                                                                                                                                                              |
| T-05 | Metadata `issuer` equals JWT `iss`, and the JWKS contains no private parameters.                                                                                                                                                                                                                                                  |
| T-06 | Verification behaves as designed throughout prepublishing a new key, confirming matching JWKS across every serving version, waiting for caches, switching keys, and removing the old key after old JWTs expire. Gradual deployment and rollback limits are also tested.                                                           |
| T-07 | Issued JWTs, issuer private keys, and exchanged credentials never appear in standard logs or error responses.                                                                                                                                                                                                                     |
| T-08 | When audience policy is RS256, a caller request for ES256 cannot change it. With ES256 opt-in, other audiences remain on RS256, and the relying party accepts both the mixed JWKS and metadata.                                                                                                                                   |
| T-09 | The mapping among `kid`, public key, and `alg` remains consistent; key reuse, duplicates, and public private-key parameters are rejected.                                                                                                                                                                                         |
| T-10 | Zod rejects unknown admin API fields, invalid TTL/alg/aud, missing `ctx.props`, and invalid DB rows. Bypassing browser validation does not change the server decision.                                                                                                                                                            |
| T-11 | A UI key-generation request returns only the public JWK and `kid`. The private key never appears in the browser, Admin Worker, D1, Workflow payload or step result, or standard logs. The Controller-generated key signs successfully through the matching issuer secret binding.                                                 |
| T-12 | Automatic rotation preserves the order: prepublish, verify secrets across serving versions, wait for relying-party caches, issue with the new key, and retire the old key after old JWTs expire. Deployment conflicts, missing observations, API failures, duplicate schedules, and retries stop or safely resume the transition. |
| T-13 | From `T_publish` through `T_remove`, the JWKS contains the old and new public keys. New tokens use only the old key before activation and only the new key afterward. A delayed activation extends overlap, and an unknown upper bound on old-key issuance prevents automatic removal.                                            |
| T-14 | A race test covers the reservation, deadline, and completion of old-key issuance started immediately before activation, proving the upper bound on old-key issuance. A remaining reservation or unproven deadline prevents automatic removal.                                                                                     |
| T-15 | Returning an audience from ES256 to RS256 succeeds only while a suitable old-algorithm key and secret binding remain. Policy cannot return to a retired key.                                                                                                                                                                      |
| T-16 | The per-client rate limit holds under concurrent and distributed requests and denies excess issuance. Failure of rate-limit state must not broaden access.                                                                                                                                                                        |

## 3. External interoperability gates

For every integration declared supported, run the following in an isolated real environment and record the procedure, metadata, positive and negative results, date, and product-specification links. A local signing and JWKS test never proves provider support. Microsoft Entra is a future candidate and is not one of the four targets in the beta gate.

| Target                   | Required live verification                                                                                                                                                                                                                                                                                            |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AWS                      | Create an IAM OIDC provider; constrain a role by `aud` and `sub`; succeed with `AssumeRoleWithWebIdentity`; fail with another `aud` or `sub`; test key rotation. Review discovery conformance separately.                                                                                                             |
| Google Cloud             | Create a Workload Identity Pool/Provider; exchange successfully under an attribute condition restricting `sub`; fail with another `aud` or `sub`; test key rotation.                                                                                                                                                  |
| Claude API               | Configure a federation issuer, service account, workspace/scope, and rule restricting `aud` and `sub`; exchange through the JWT bearer grant and call the API with least privilege. Also test incorrect `aud`/`sub`, expiry, rotation, JWKS retrieval and caching, and the exchanged-token lifetime.                  |
| OpenAI API               | Confirm whether an arbitrary issuer can be registered. Attempt provider/mapping configuration and token exchange with this issuer. If accepted, test incorrect `aud`/`sub`, a least-privilege API call, rotation, and JWKS retrieval and caching. If not accepted, record it as unsupported and do not claim support. |
| Microsoft Entra (future) | Before claiming support, verify exchange when issuer/subject/audience match, failure when they differ, and behavior after key rotation.                                                                                                                                                                               |
| Private API              | Verify signature, `iss`, a single `aud`, `sub`, time, key updates, and token-purpose separation.                                                                                                                                                                                                                      |

AWS, Google Cloud, Claude API, and OpenAI API are **evaluation targets**, not supported integrations. The beta is released only after the live validation of all four; [Release status](../reference/release-status.md) is the single source of truth for the beta gate. Unsupported or unverifiable outcomes are valid results; only successful targets appear in a supported list. See the [provider validation plan](./provider-validation.md) and [Provider support](../reference/provider-support.mdx).

Algorithm-specific tests follow the [key and algorithm specification](./key-management.md). Declaring an algorithm other than RS256 supported requires live evidence that the audience's relying party accepts both the algorithm and a mixed JWKS.

## 4. Operations gate

The passkey, Cloudflare Access, RBAC, CSRF, audit, initial-admin, and recovery tests must satisfy the [admin console acceptance criteria](./admin-console.md#6-admin-console-acceptance-criteria). Production configuration selects one authentication mode explicitly and never falls back implicitly.

- Rehearse normal rotation and compromise response; explain old-key removal using observed or documented relying-party cache behavior.
- Cover the lifetime of already-issued JWTs and temporary cloud credentials after a caller is disabled.
- Detect public-metadata, issuance, and client-registration failures independently.
- Do not describe an unverified cloud or OIDC conformance as supported in the README or release notes.

The beta gate, including the live validation of AWS, Google Cloud, Claude API, and OpenAI API, secret scanning, and the security reporting channel, is listed only in [Release status](../reference/release-status.md).

## 5. Current local evidence

The caller SDK and shared issuer contract are implemented. `packages/client/src/index.test.ts` and the type-test file `index.typecheck.ts` cover forbidden arguments, invalid configuration, response shape, public error classification, and the absence of retries and caching.

`apps/issuer-worker/test/issuance.test.ts` uses a temporary RSA key and local D1 in workerd to test SDK issuance, RS256 verification with the public JWKS, immediate client-disable and grant-removal effects, missing props and forged-argument rejection, shared rate limiting, fail-closed configuration and DB errors, and the absence of HTTP issuance. These provide local evidence for A-01, A-02, A-03, A-06, T-01, T-02, T-03, T-05, and T-16; they do not complete the production-equivalent gates.

A test loopback does not substitute for a real Service Binding from a separate Worker with fixed props. A-04 effective permissions, production-like Worker communication, rotation, admin console and API acceptance, and external interoperability remain incomplete. The [caller library acceptance criteria](./client-library.md#acceptance-criteria) also apply.
