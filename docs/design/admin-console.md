# Admin console, authentication, and operational requirements

**Status:** Implemented. The admin console supports client, grant, and audience editing with change review; operator roles, suspension, and deletion; Access identity linking and unlinking; additional passkeys and their deletion; recovery invitations; audit search with pagination; per-audience relying-party confirmations; aggregate issuance metrics; and public health monitoring. See [Rotation Controller](./rotation-controller.md) for rotation approval, pause, resume, automation, and immediate rotation, and [Operations](../guides/operations.md) for migrations and recovery. Some acceptance criteria below are production goals that still require live verification.

## 1. Deployment and responsibilities

Place the admin console and admin API in a **dedicated Admin Worker**. In passkey mode, use `<issuer path>/admin/` on the issuer's public hostname as the entry point and let the issuer Worker forward it to the Admin Worker. Keep OIDC discovery/JWKS, issuance RPC, and admin API responsibilities separate. [Public host and root path](./domain-routing.md) is authoritative for issuer and admin routing.

The Admin Worker serves a Hono JSON API and a SPA built with React and Vite from the same admin origin and base path. The SPA uses TanStack Router and TanStack Query for navigation and data fetching, Cloudflare Kumo and Tailwind CSS v4 for components and styling, i18next for English and Japanese text, and ECharts for issuance charts. See [Admin console frontend selection](./frontend-selection.md). Restrict routes needed before authentication, such as login, authentication challenges, and initial invitation redemption, to an explicit allowlist, with rate limits, short expiration times, and single-use processing. Apply the same authentication and authorization to all other admin API routes. Static shells/assets in passkey mode must contain no secrets; in Access mode, protect the entire admin path with Access. The Admin Worker must not access issuance private keys or Cloudflare Worker update tokens, or issue JWTs on behalf of callers.

Separate D1 into a **Policy DB**, **Admin DB**, and **Key Registry DB** for each environment. The Policy DB stores clients, audiences, grants, and policy change audits; the Admin Worker writes to it, and the issuer Worker reads it during issuance. The Admin DB stores operators, passkeys, challenges, admin sessions, and operator action audits; only the Admin Worker receives a Binding to it. The Key Registry DB stores public JWKs, key states, and rotation history; the Rotation Controller writes to it, and the issuer Worker reads it. The Admin Worker displays key information through the Controller's restricted RPC interface. Ensure the issuer cannot read operator credentials. During issuance, the issuer reads the client's enabled status and allowed audiences from the primary Policy DB. **Do not use read replicas or time-limited local caches for authorization decisions that must reflect disabling.** Reject new issuance if the Policy DB is unavailable. D1's `batch()` can execute multiple statements as a single transaction. [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/), [D1 read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/)

## 2. Authentication adapters

Production `ADMIN_AUTH_MODE` must be **exactly one of** `passkey` or `cloudflare-access`. The Admin Worker validates its configuration with Zod (`adminConfig()`) on every request rather than at startup. A missing or malformed value (for example an unknown `ADMIN_AUTH_MODE`, an `ADMIN_ORIGIN` that is not an `https://` URL, a `CSRF_SECRET` shorter than 32 characters, a missing `RP_ID`, or a missing `ACCESS_*` value) fails schema validation, and every request fails with HTTP 400 and the error code `invalid-input`. Settings that are well formed but inconsistent (an `ADMIN_ORIGIN` that is not a bare origin, an `RP_ID` that does not match the `ADMIN_ORIGIN` host name, Access settings in passkey mode or `RP_ID` in Access mode, or a step-up origin or AUD equal to the main one) make every request fail with HTTP 503 and the error code `unavailable`. Settings the Worker does not read are ignored. Do not expose passkey authentication or registration APIs in Access mode, and do not treat Access headers as authentication in passkey mode. Do not implicitly fall back from production settings to a development environment.

Both adapters normalize authenticated principals to the same structure.

```ts
type AuthenticatedOperator = {
  provider: "passkey" | "cloudflare-access";
  providerSubject: string;
  operatorId: string;
  authenticatedAt: number;
};

interface AdminAuthProvider {
  authenticate(request: Request): Promise<AuthenticatedOperator | null>;
  registerRoutes(app: AdminApp): void;
}
```

This is a conceptual interface; implementation type names may differ. Adapters handle identity verification, while **the shared authorization layer checks the local operator record's enabled status and role on every request**. Do not use email addresses or display names as identifiers or the basis for permissions. Do not automatically link accounts when changing authentication methods; require explicit migration and auditing by an existing security admin.

### Passkey mode

- WebAuthn registration and authentication use `@simplewebauthn/server` and `@simplewebauthn/browser`. Do not implement custom WebAuthn cryptography. [SimpleWebAuthn](https://simplewebauthn.dev/docs/packages/server)
- Fix `rpID` to the exact public hostname shared by the issuer and admin console and `expectedOrigin` to its HTTPS origin. The discovery and JWKS routes do not process WebAuthn, and credentials are sent only to admin authentication APIs.
- Generate registration and authentication challenges from random values and store them in D1 for short-term, single-use processing. Verify the challenge, origin, RP ID, user verification, signature, and credential ID on the server. Set `userVerification: "required"`; the initial release does not request attestation during registration.
- Store credential public keys, IDs, sign counters, creation/last-used timestamps, and user associations. Synced passkeys may have a counter of 0; do not incorrectly reject them on that basis alone. An operator can register at most 10 passkeys.
- After authentication, issue a high-entropy opaque session ID and store its hash in D1. Set cookies to `Secure`, `HttpOnly`, and `SameSite=Lax` or stricter, and reissue them on login to prevent session fixation. Sessions expire after 8 hours. Enforce revocation and logout on the server.
- Pre-authentication passkey endpoints are rate limited to 20 requests per minute per client IP address.
- Do not automatically promote the "first visitor" to initial administrator. An operator with deployment permissions creates a single-use invitation through a CLI/bootstrap procedure, and the recipient registers a passkey before its short expiration. If a passkey is lost, use re-registration by another security admin; if everyone loses access, use an audited CLI recovery procedure. Do not provide unconditional email-based recovery.

### Cloudflare Access mode

- Protect the **entire admin path** (`<issuer path>/admin/*`) on the public host with a Cloudflare Access application. Keep discovery and JWKS public, and apply Access to the UI, admin APIs, static assets, and auxiliary routes. In production, close unprotected alternative routes such as `workers.dev`, or at minimum guarantee equivalent rejection through in-application JWT validation.
- On every admin request, verify the signature of `Cf-Access-Jwt-Assertion` using Access public keys, and check the configured team domain's `iss`, application AUD tag, `exp`/`nbf`, `type=app`, and a nonempty human `sub`. Do not accept Cloudflare Access service tokens for human admin console login. The presence of a header alone must not establish authentication. [Cloudflare Access JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/), [token claims](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/)
- Fix `providerSubject` to the verified Access `iss` + `sub` and explicitly associate it with a local operator. Do not automatically create operators merely because they passed Access. Do not synchronize roles from Access groups in the initial release; use local RBAC as the basis for permissions.
- In Access mode, do not use the admin application's own login session as proof of identity. Validate the Access JWT and check the local operator on every request. Follow Access key updates by fetching public keys again, and fail closed if a fetch failure prevents validity checks.

#### Access reauthentication for high-impact operations

Use a **step-up Access application** separate from the regular admin Access application for nine high-impact actions: `operator.create`, `operator.update`, `operator.delete`, `operator.recover`, `rotation.plan`, `rotation.approve`, `rotation.control`, `rotation.schedule`, and `rotation.immediate`. The step-up application protects the entire **separate HTTPS host** specified by `ACCESS_STEP_UP_ORIGIN`, which routes to the same Admin Worker as the regular admin host. Separate the Access cookies and AUD tags for the two hosts. Configure the step-up application with the same human user requirements as the regular admin application, or stricter requirements. The Worker accepts only regular routes on the regular host and `GET /api/access-step-up/complete` on the step-up host, rejecting requests sent to the wrong host. [Access authorization cookie](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/)

Require Cloudflare Access independent MFA for the step-up application, set the MFA authentication duration to **Require every login**, and set both application and policy session durations to **5 minutes or less**. Disable session duration overrides through Cloudflare One Client authentication, and do not configure Bypass or Service Auth policies. Distinguish regular admin application Access JWTs from step-up application JWTs using `ACCESS_AUD` and `ACCESS_STEP_UP_AUD`; treat equal or missing values as configuration errors. `ACCESS_STEP_UP_ORIGIN` is also required and must differ from the regular `ADMIN_ORIGIN`. An Access JWT's `iat` does not itself prove MFA. The Worker verifies that the step-up application's signed JWT was issued within the past 5 minutes; MFA enforcement depends on the step-up application's policy. [MFA reauthentication settings](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/mfa-requirements/), [session duration](https://developers.cloudflare.com/cloudflare-one/access-controls/access-settings/session-management/)

For an operation, create a 2-minute challenge in Admin D1 under regular Access authentication, local RBAC, and Origin/CSRF checks, binding it to the operation type, operator ID, and Access `iss`+`sub`. The admin console opens the step-up host in a separate window. The Worker verifies the JWT for the step-up AUD, an enabled operator associated with the same Access principal, operation permissions, and JWT issuance time, then completes the challenge. The original page checks completion through the regular host's API and passes the challenge ID to the high-impact POST. The Worker checks the operation type, operator, Access principal, expiration, and completion status, then **atomically consumes it exactly once**. Reject use for a different operation or operator, expiration, reuse, and JWTs for the regular AUD. Reject the high-impact POST if step-up fails or is misconfigured. Regular admin APIs and static pages remain protected by the regular Access application and cannot be accessed with a step-up JWT alone. The challenge remains consumed even if the operation itself fails temporarily, so retries require a new step-up verification.

For production rollout, proceed in this order: (1) apply the Admin D1 migrations `0002_access_step_up.sql`, `0004_step_up_actions.sql`, and `0005_rename_immediate_rotation.sql`; (2) assign the admin and step-up hosts to the same Worker and close unprotected alternative routes; (3) configure the separate Access applications and policies described above for each host; (4) configure `ADMIN_ORIGIN`, `ACCESS_STEP_UP_ORIGIN`, and both AUDs on the Worker. Do not consider production high-impact operations enabled until Access authentication on both hosts, the MFA screen, each high-impact action, and rejection of challenge reuse have been verified in the actual environment. The staging `workers.dev` deployment procedure is for passkey mode only and does not create this Access configuration.

## 3. Authorization and initial administrator

| Role             | View    | Modify client/audience/grant | Emergency client disable | Operator management/authentication migration | Approve key rotation |
| ---------------- | ------- | ---------------------------- | ------------------------ | -------------------------------------------- | -------------------- |
| `viewer`         | Allowed | Denied                       | Denied                   | Denied                                       | Denied               |
| `operator`       | Allowed | Allowed                      | Allowed                  | Denied                                       | Propose only         |
| `security-admin` | Allowed | Allowed                      | Allowed                  | Allowed                                      | Allowed              |

Register the initial `security-admin` through a CLI/bootstrap procedure tied to deployment permissions. In Access mode, associate the Access `iss` + `sub`; in passkey mode, associate the operator ID created through an invitation. Do not provide a public "make the first user an administrator" page. Prohibit disabling or deleting the last enabled `security-admin`. Prohibit self-promotion through permission changes or operator creation, and record both the actor and target in the audit log.

Enforce authorization on the server for changes made by an `operator` as well. Do not rely solely on hiding buttons. For the nine high-impact actions listed above, the server requires an authentication timestamp within the past 5 minutes in passkey mode, or the step-up challenge described above in Access mode. Adding or deleting a passkey also requires authentication within the past 5 minutes. Confirm the target and changes on screen before execution.

The admin console must not display or download JWT bodies, issuer private keys, or temporary cloud credentials. Even when "Generate" is clicked, only public keys and progress are returned to the browser; the Rotation Controller generates and uploads private keys on the server. The admin API must require the same authentication and authorization as the admin console and must not be exposed as a general-purpose external admin API. If a machine administration API is needed in the future, design explicit authentication and permissions separate from human authentication.

## 5. Data and update rules

The migrations under [`migrations/`](https://github.com/akita0724/workers-workload-identity/tree/main/migrations) create these tables:

| Database        | Tables                                                                                                                                                                                                          |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admin DB        | `operators`, `operator_identities`, `passkey_credentials`, `webauthn_challenges`, `auth_rate_limits`, `admin_sessions`, `bootstrap_invites`, `admin_audit_events`, `access_step_up_challenges`, `health_checks` |
| Policy DB       | `clients`, `audiences`, `client_audience_grants`, `policy_audit_events`, `issuance_rate_limits`, `issuance_metrics`, `issuance_audit_events`                                                                    |
| Key Registry DB | `signing_keys`, `issuance_reservations`, `rotation_runs`, `rotation_evidence`, `rotation_schedules`, `rotation_proposals`, `rotation_actions`                                                                   |

Access mode does not use passkey-specific tables. Do not store issuance key private material in any D1 database.

Validate all admin API inputs and runtime settings with Zod schemas, and reject unknown fields using `z.strictObject(...)` or equivalent. Do not trust rows read from the database; validate them with Zod at the boundary where they are converted into issuance policies. Infer TypeScript types from schemas, and treat UI validation as supplementary. [Zod basics](https://zod.dev/basics)

Client/audience/grant changes carry a `version` for optimistic concurrency, and the update and audit event append are committed in the same D1 transaction in the Policy DB. Structure SQL and transactions so that no audit event is written if a conditional update affects 0 rows; return 409 for conflicts and prompt the user to review the differences again. Commit administrator/passkey change audits similarly in the Admin DB, and combine events from both databases in the audit screen. To make permission reductions such as disabling effective from the issuer's next issuance request, the issuer reads the Policy DB on every issuance and does not cache authorization results across requests. Do not apply changes if authentication, authorization, D1, or audit writes fail. There is no distributed transaction between the Admin DB and Policy DB, so do not provide operations that change administrator state and policies together.

The admin API must address CSRF associated with cookie authentication by strictly checking a fixed origin and using CSRF tokens for state-changing methods. Hono's CSRF middleware checks `Origin` and `Sec-Fetch-Site`, but applies only to certain content types, so cover all mutation routes, including JSON APIs, with additional checks. [Hono CSRF middleware](https://hono.dev/docs/middleware/builtin/csrf)

## 6. Admin console acceptance criteria

- In both authentication modes, unauthenticated users, failed authentications, unregistered operators, and disabled operators cannot use any admin screen or admin API route.
- Reject passkey challenge reuse, incorrect origins/RP IDs, insufficient user verification, and signatures from a different credential.
- Validate Access JWT signatures, `iss`, `aud`, expiration, and nonempty human `sub`; reject JWTs from other Access applications and service tokens.
- In Access mode, reject each of the nine high-impact actions without an operation-specific, operator-specific challenge created within the past 2 minutes that has passed the step-up application's MFA. Also reject completion with the regular AUD, stale step-up JWTs, use by a different Access principal/operator or for another operation, expiration, and reuse.
- Enforce viewer/operator/security-admin permission boundaries, protection of the last security-admin, and prevention of self-promotion on the server.
- Reject disabled clients on their next issuance request. Conflicting updates fail, and audit events are recorded in the same transaction as the corresponding update.
- Policy DB and Admin DB audits are searchable in the admin console, and a change is not committed if its audit write fails.
- Admin APIs outside the pre-authentication allowlist have authentication and CSRF protection, and the admin console does not expose private keys or JWT bodies. Passkey static shells/assets do not expose admin data. Pre-authentication routes enforce rate limits and single-use challenges/invitations.
- In Access mode, in-application JWT validation fails even when the Admin Worker is called through an alternative URL outside Access protection.
- The key generation button can start an execution job, but private keys and Cloudflare API tokens never reach the browser, Admin Worker, or D1. Key switches cannot bypass failed gates, and automation can be enabled only for verified targets.
