Every external provider is currently **unverified**. A provider may document a compatible protocol, but this project does not declare support until a real token exchange with this issuer succeeds.

The issuer publishes AWS IAM's requested `issuer`, `jwks_uri`, `claims_supported`, `response_types_supported`, `subject_types_supported`, and `id_token_signing_alg_values_supported` fields. `id_token_signing_alg_values_supported` is the static list `["RS256", "ES256"]`, not the keys currently in the JWKS. The last three fields are workload federation compatibility metadata; they do not imply an OIDC authorization endpoint or ID Token flow. Live AWS validation remains outstanding. [AWS IAM requirements](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_create_oidc.html)

:::warning
“Unverified” does not mean known to be incompatible. It separates compatibility inferred from public documentation from interoperability observed in a target account.
:::

## Evidence required for support

For each provider, verify at least:

- issuer and JWKS registration, key retrieval, and cache refresh;
- success with the intended `iss`, `aud`, and `sub`;
- rejection when each claim is wrong;
- accepted algorithms and handling of an unknown `kid`;
- permissions and maximum lifetime of exchanged credentials;
- effect of client disablement, grant removal, and relying-party revocation;
- normal and immediate key rotation; and
- caller behavior under rate limits, timeouts, and transient failures.

Record the date, environment type, algorithm, audience format, observed cache duration, and both positive and negative cases. Never publish real account IDs, role ARNs, provider IDs, JWTs, or access tokens.

## Do not confuse exchange with direct API authentication

For AWS, Google Cloud, and Microsoft Entra, the caller sends the issuer JWT to the provider's exchange endpoint and receives temporary credentials. Claude API and OpenAI API similarly require a federation token endpoint to accept the assertion before the caller sends the exchanged access token to the normal API.

Do not send an issuer assertion directly as a normal API Bearer token. A private API may accept it directly only when that API implements the rules in [Verify an assertion](../guides/verifying-assertions.md).

The [live provider validation plan](../design/provider-validation.md) covers the four initial targets and also describes Microsoft Entra and Oracle Cloud Infrastructure. [Specifications and primary sources](../design/references.md) also covers Microsoft Entra. Live validation of Microsoft Entra and Oracle Cloud Infrastructure is outside the beta gate.
