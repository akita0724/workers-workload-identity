# Admin Worker

The Admin Worker serves the admin API and the built admin console (`apps/admin-ui`) from the same origin. It authenticates operators, enforces role-based access control (RBAC) through `packages/domain-operators`, and stores policy in the Policy D1 database and operator data in the Admin D1 database. Key rotation requests go to the Rotation Controller through the `ROTATION` Service Binding (`RotationRpc` entrypoint, `props: { "caller": "admin" }`). The Admin Worker never holds private signing keys or a Cloudflare API token that can update Workers.

## Authentication modes

`ADMIN_AUTH_MODE` selects one of two modes. Each mode rejects the other mode's settings.

- **Passkey mode (`passkey`):** Operators sign in with passkeys (WebAuthn). `RP_ID` must equal the host name of `ADMIN_ORIGIN`. The first administrator is registered from a one-time invitation.
- **Cloudflare Access mode (`cloudflare-access`):** Cloudflare Access authenticates operators in front of the Worker, and the Worker verifies the Access JWT. Set `ACCESS_TEAM_DOMAIN`, the admin application's audience tag in `ACCESS_AUD`, and a separate Access application that requires MFA in `ACCESS_STEP_UP_AUD`. High-impact operations re-authenticate through that application on a separate host, `ACCESS_STEP_UP_ORIGIN`, which must differ from `ADMIN_ORIGIN` and route to the same Worker.

For Access policies, session lifetimes, and how to apply the D1 migrations, see [Access reauthentication for high-impact operations](../../docs/design/admin-console.md#access-reauthentication-for-high-impact-operations) in the admin console design.

All modes require the `CSRF_SECRET` secret. Requests whose origin does not match `ADMIN_ORIGIN` (or `ACCESS_STEP_UP_ORIGIN` for the step-up callback) get 404. If the configuration is invalid, the Worker does not authenticate anyone. A missing or malformed value (such as `ADMIN_AUTH_MODE`, `ADMIN_ORIGIN`, a `CSRF_SECRET` shorter than 32 characters, `RP_ID`, or an `ACCESS_*` value) makes every request fail with 400 and `{"error":"invalid-input"}`. Well-formed but inconsistent settings (an `RP_ID` that does not match the `ADMIN_ORIGIN` host, Access settings in passkey mode or `RP_ID` in Access mode, or a step-up origin or AUD equal to the main one) make every request fail with 503 and `{"error":"unavailable"}`. Settings the Worker does not read are ignored.

## Configuration example

`wrangler.example.jsonc` shows Access mode on its own hosts (`admin.example.com` and `admin-step-up.example.com`). The staging setup generated by `pnpm staging:configure` instead uses passkey mode and serves the console at `<issuer>/admin/` through the issuer's optional `ADMIN` Service Binding, setting `ADMIN_BASE_PATH` so the console's links stay under that path.

A cron trigger runs every five minutes to delete expired sessions, WebAuthn challenges, step-up challenges, invitations, and old rate-limit rows.

## Status

This package contains an initial implementation of the admin API, authentication, and RBAC, plus `wrangler.example.jsonc`. Production configuration, migrations, authentication policies, and operational acceptance are not finished. Do not deploy it to production as is.

```sh
pnpm --filter @workers-workload-identity/admin-worker typecheck
pnpm --filter @workers-workload-identity/admin-worker test
```
